# 91 設計レビューチェックリスト（5 観点 29 項目）

> いつ読むか: review モード。scaffold 後のセルフレビュー、本番投入前ゲートにも使う。
> 出典: 第 9 章 9.3、第 10 章 10.5.5（要約・再構成）

## 運用ルール

- 判定は **適合 / 要改善 / 未対応** の 3 段階
- **S 項目（セキュリティ）は本番前に全項目適合が必須**（途中ゲート。1 つでも未対応なら差し戻し・修正必須）
- 他観点は要改善 3 項目以内なら改善計画を立てて本番投入を判断できる
- 使うタイミング: 設計レビュー（全項目）/ PR レビュー（関連項目）/ 本番投入前（全項目）/ 四半期定期（全項目）
- 実行順: 変更対象と影響範囲を整理 → A → S（ゲート）→ O → C → Q → 判定

## A. アーキテクチャ

| # | 項目 | 確認内容 | 確認方法（コード上の手がかり） | 原則 |
|---|---|---|---|---|
| A-1 | 単一責任 | 各エージェントの責務は 1 つか | Instruction を 1〜2 文で言えるか。「〜して、〜して」が 3 つ以上ないか | 1 |
| A-2 | エージェント分割 | ツールが 5 個以下か（10 個超は分割推奨） | `tools=[...]` の要素数（McpToolset は公開ツール数も見る） | 1 |
| A-3 | オーケストレーション | Sequential / Parallel / Loop / Graph / Dynamic を用途に応じて使い分けているか | 依存関係があるのに Parallel、固定手順なのに LLM 委譲、`LoopAgent` に `max_iterations` | 1 |
| A-4 | 疎結合 | エージェント間の依存が A2A / State 経由に限定されているか | 他エージェントの内部関数を直接 import していないか | 8 |
| A-5 | スケーラビリティ | 各エージェントを独立してスケールできるか | トラフィック特性の異なるものが同一デプロイ単位か | 8 |
| A-6 | Instruction 構造 | 構造化され 500 トークン以内か | セクション見出しの有無、文字数（日本語はおおむね 1 文字 ≒ 1 トークン強で概算） | 6 |

## S. セキュリティ（ゲート）

| # | 項目 | 確認内容 | 確認方法 | 原則 |
|---|---|---|---|---|
| S-1 | 最小権限 | 必要最小限のツールのみ付与 | `delete_*` / `drop_*` / `execute_sql` / `run_command` が読み取り用途のエージェントにないか | 2 |
| S-2 | 入力検証 | ユーザー入力のサニタイズ | 入力長制限・パターン検出の有無 | — |
| S-3 | Prompt Injection | 対策（ガードレール等）が実装されている | `before_model_callback` にインジェクション検出があるか。Instruction にセキュリティルールがあるか | — |
| S-4 | 認証情報管理 | API キー・認証情報の直書きなし | `API_KEY = "..."` / `sk-` / `AIza` リテラル、`.env` が `.gitignore` にあるか | — |
| S-5 | データ保護 | 機密情報がログに出ない | ログ出力前の PII マスク、State に auth_token / api_key を入れていないか | — |
| S-6 | 権限制御 | 書き込み操作の権限チェックが `before_tool_callback` にある | RBAC / TOOL_PERMISSIONS の有無 | 2 |
| S-7 | Kill Switch | 緊急停止の仕組みがある | before_model / before_tool に停止判定があるか | 9 |
| S-8 | 出力フィルタリング | LLM 出力に機密情報が含まれないことを確認 | `after_model_callback` のマスク / 検出 | — |

補助: `80-security.md` のセキュリティレビューチェックリスト（脅威モデル文書化 / 入力防御 / 出力防御 / 認証認可 / Kill Switch / 監査 / ガバナンス）。

## レポートフォーマット

`templates/review/design-review-report.md` を使う。要点: サマリー → 判定表（観点別、結果と詳細、該当アンチパターン）→ ゲート判定（S 全件適合か / 要改善 3 以内か）→ 改善提案（優先度順、【緊急】から、コード例付き）→ 次のステップ。低 severity（Q-1 など）も省略せず全 5 観点を出す。
