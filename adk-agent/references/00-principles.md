# 00 設計の土台 — 6 つの壁・3 軸体系・設計原則 10

> いつ読むか: design / review モードの最初。設計判断の「理由」をここから引く。
> 出典: 書籍「はじめに」、第 1 章、第 9 章 9.1 節（要約・再構成）

## ラストワンマイルと 6 つの壁

AI エージェントの PoC は多くが本番に届かない。書籍はこれを **PoC 80 点 → 本番 90 点** の 10 点差として捉え、越えるべき壁を 6 つに整理する。

| 壁 | 症状 | 主な対処（章） |
|---|---|---|
| 精度の壁 | モデルを替えても頭打ち。記憶・検索の設計が雑 | Memory Engineering（3・4 章） |
| トークンコストの爆発 | 本番で PoC の 3〜5 倍消費 | Context 予算・Compaction・キャッシュ（3・4・8 章） |
| マルチエージェント設計 | 責務分解・通信・失敗時リカバリで破綻 | 協調パターン・A2A（7 章） |
| モデル選定 | ID・料金・レイテンシが変わる | 評価結果を基準に見直す（2・8 章） |
| ログ・Observability | Web アプリのログ設計では追えない | LLM / ツール / Session 各層のトレース（8 章） |
| ハーネス | 自律性と安全性の両立 | 評価・ガードレール・HITL（5・10 章） |

到達点の目安: 2〜4 章で 80 点の土台、5 章 82、6 章 84、7 章 86、8 章 88、10 章で 90。95 点（企業データでの Memory 最適化）と 100 点（業務プロセス全体への HITL 定着）は現場でしか磨けない。

## エージェントの基本モデル

- **定義**: 目標達成のために自律的に動作し、観測 → 理解 → 計画 → 行動 → 評価を反復するソフトウェア。LLM ラッパーとの違いは **自律性・ツール使用・計画能力** の 3 要件
- **中核コンポーネント 6 つ**: 推論エンジン（LLM）／ツール群／メモリ（Session・State・Memory）／実行環境（adk run・Agent Engine・Cloud Run・GKE）／ガードレール（コールバック）／観測と評価（adk eval・conformance・トレース・ログ）
- **3 類型**: 自律性重視（定型業務。Agent + ツール + ガードレール）／知性重視（複雑分析。Context Engineering が成否を決める）／ハイブリッド HITL（承認が必要な業務）
- **品質特性 6 つ**: 成功率・反復回数・コスト・レイテンシ・安全性・再現性。すべて本番でも監視し続ける
- **開発 7 フェーズ**: 要件化 → 設計 → プロトタイプ → 評価 → 改善 → 本番化 → 運用学習（循環）

## ADK が下した 4 つの設計判断（設計意図を理解して使う）

1. **エージェント型を型で分ける** — `Agent`（LLM 推論）/ `Workflow`（明示グラフ）/ `@node`（コード制御）/ Template Workflow（Sequential・Parallel・Loop）/ `BaseAgent` 継承。理由は合成可能性。定型制御は Template、複雑な制御は Workflow Runtime で明示する
2. **コンテキストを用途で分離** — `InvocationContext`（内部）/ `ReadonlyContext`（Instruction 生成、書込不可）/ `Context`（コールバック・ツール・ノード。`CallbackContext` `ToolContext` は互換エイリアス）。最小権限の原則を型で表現し、副作用の混在をレビューで見つけやすくする
3. **Session / State / Memory の三層** — 揮発性から永続性へのグラデーション。単一ストアだとコスト・ノイズ（コンテキスト汚染）・スケーラビリティ・プライバシーで破綻する
4. **評価を CLI に組み込む** — 非決定的な出力に TDD は効かない。評価セットを定義し `adk eval` で測り続ける **評価駆動開発**。`adk conformance` で記録済み挙動との整合を回帰テストする

## 3 軸体系

| 軸 | 問い | 主な ADK 機能 |
|---|---|---|
| Context Engineering | LLM に何を見せるか | コンテキスト型、Instruction、コールバック、Agent Skills、Compaction |
| Memory Engineering | 何を覚え、何を忘れるか | Session、State、Memory Bank、RAG Engine |
| Harness Engineering | 何をさせ、何をさせないか | adk eval、ガードレール、HITL、User Personas、conformance |

3 軸は連携する: Instruction が参照する情報は Memory が供給し、Instruction が機能しているかは Harness の評価で検証し、Memory の記憶が正しいかはガードレールで担保する。偏りは品質低下か事故につながる。

## 設計原則 10（判断基準付き）

実装コストとリスク低減効果の 2 軸で優先度を付ける。**最優先（低コスト・高効果）**: 単一責任・最小権限・フェイルセーフ・冪等性。**戦略的投資（高コスト・高効果）**: 可観測性・評価駆動・疎結合協調・段階的自律性。**余裕があれば**: コンテキスト最小化・コスト意識。

| # | 原則 | 要点 | 判断基準 |
|---|---|---|---|
| 1 | 単一責任エージェント | 1 エージェント 1 責務。指示が増えるほど各指示の遵守率が下がる | Instruction を 1〜2 文で説明できないなら分割。「〜して、〜して、〜する」が 3 つ以上なら分割サイン |
| 2 | 最小権限 | LLM は確率的にツールを選ぶ。不要なツールは意図しない呼び出しと被害範囲を生む | 「このツールが無くてもタスクは完了するか」に Yes なら付与しない |
| 3 | 冪等性 | リトライ・再送・adk eval の繰り返し・複数エージェントの同時到達を 1 回の処理に収束させる（冪等キー + upsert） | 「2 回連続で呼んだら何が起きるか」が「同じ結果」でなければ設計が必要 |
| 4 | 可観測性 | トレース・ログ・メトリクスを最初から。OpenTelemetry + コールバックでカスタムメトリクス | 「本番で問題が起きたときトレースから動作を再構成できるか」に No なら不足 |
| 5 | 段階的自律性 | FULL_HITL(0) → SUPERVISED(1) → SEMI_AUTONOMOUS(2) → AUTONOMOUS(3)。ツールのリスクレベルと組み合わせて承認要否を決める | 新規エージェントは必ずレベル 0 から。1〜2 週間で承認率 95% 超なら次へ |
| 6 | コンテキスト最小化 | Lost in the Middle。必要な情報はツールで動的取得、履歴は Compaction | Instruction が 500 トークンを超えたら外部化（ツール化・RAG 化・Agent Skills） |
| 7 | 評価駆動 | 評価セットを先に作り改善サイクルを回す。失敗事例は都度評価ケースに追加 | コードを書く前に最低 5 件、本番前 30 件以上 |
| 8 | 疎結合協調 | A2A（Agent Card + 標準メッセージ）で内部実装に依存しない連携。独立デプロイ・障害分離 | A の内部変更で B の修正が必要なら結合度が高すぎる |
| 9 | フェイルセーフ | ツールレベルのリトライ・フォールバック／エージェントレベルのループ検知／システムレベルの Kill Switch の 3 レイヤー | 「外部サービスが全部落ちたら」「LLM が意味不明な出力を返したら」の答えがクラッシュや無限ループなら不足 |
| 10 | コスト意識 | モデル設定・コンテキスト管理・キャッシュの 3 レイヤーで最適化。コスト監視コールバック | 本番前に 1 リクエスト平均コストと月間想定を計算。予算の 80% 超なら最適化を優先 |

コスト最適化手法の効果目安: モデル設定見直し（大・低コスト）、レスポンスキャッシュ（大・中）、Compaction（中・低）、Instruction 最適化（中・低）、バッチ処理（大・高）。

## 原則同士の関係

単一責任 → 短い Instruction と少ないツール → コスト意識に貢献。評価駆動 → 段階的自律性の判断材料。疎結合 → セキュリティの障害分離。運用のログ設計 → コスト監視の基盤。設計レビュー（`91-review-checklist.md`）はこれらを 5 観点 29 項目に落としたもの。
